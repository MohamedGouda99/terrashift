HLD-1

System architecture — what runs inside the single binary

Where does each crate live, and what's inside the binary vs outside?

Single binary, three layers. cli/ and tui/ are the user surface; libs/engine holds the migration pipeline; libs/* below it are the Foundation crates that the engine depends on. Everything compiles into one statically-linked binary with rustls-tls — no Node, no Python, no JVM. The two crates with terracotta borders (libs/creds, libs/audit) are the security-sensitive ones where Article V enforcement happens.

Storage (SQLite for state, LanceDB for vectors) is embedded — they're libraries linked into the binary, not separate services. The only network calls are to LLM providers (via stakai), cloud APIs (federated short-lived tokens only), and VCS. terraform plan/apply runs in a sandboxed Docker container per migration but Docker isn't required for distribution — only for executing migrations.

HLD-2

Migration pipeline — 9 components, three kinds

Of the 9 components in libs/engine, which are deterministic, which are single LLM calls, and which are true agents?

Of the 9 components, 5 are pure deterministic Rust (Scanner, Generator, Validator, Executor, Verifier — no LLM at all on the happy path). 2 are LLM-with-structured-output (Mapper, Planner — single LLM call producing JSON validated by schemars schemas, then deterministic dispatch on the result). 2 are true agents (Recovery, Cost Optimizer — ReAct loops with bounded iterations, fire only on failure points).

Article I (architectural restraint) is operationalized here: most migrations complete without ever invoking an agent. Cost Optimizer fires when the cost gate triggers; Recovery fires when Executor or Verifier fails. The deterministic path is the fast happy path; agents are escape hatches with bounded blast radius.

HLD-3

Reference codebases — how the team uses them during development

When a teammate prompts Opus 4.7 with a citation like "stakpak_arch.md section 8", what actually happens?

All three references live on every team member's machine at ~/refs/. The architecture document (stakpak_arch.md) is the canonical citation: prompts say "read sectionN first" instead of "grep through Stakpak source for X". When the doc references a specific file:line, Opus descends into ~/refs/stakpak/ to verify. Claude Code source is consulted only for agent-loop conceptual patterns where its TypeScript shape is genuinely cleaner than Stakpak's Rust implementation.

The reference-explorer sub-agent (defined in .claude/agents/reference-explorer.md) is the operational mechanism: ask it to look up a pattern and it returns a 3-5 bullet summary plus a quote, never code. Generated code carries citations (// Pattern: stakpak_arch.md sectionN) so reviewers can verify intent against source-of-truth.

LLD-1

Tool execution flow — kernel-level (agent-core)

When the LLM proposes N tool calls, how does the agent kernel turn that into N executions with approval, hooks, and audit?

The agent-core kernel runs an 8-step loop per turn. Steps 1-3 happen once per inference response; steps 4-8 are the inner loop that processes each proposed tool call in declaration order. The ApprovalStateMachine is the load-bearing piece: it lets users resolve tool decisions out of order (resolve id 2 before id 1) without breaking execution order — next_index advances strictly forward.

The five hook points are how Terrashift integrates security and audit without modifying the kernel. libs/audit registers a hook on after_tool_execution to write signed entries; libs/creds registers on before_tool_execution to resolve {{secret:...}} references. Hooks return Result<()> — an Err propagates immediately and aborts the run.

LLD-2

Migration lifecycle — full path with rollback escape hatches

From "user types terrashift migrate" to "audit log signed, checkpoint saved" — what are the phases, what gets persisted at each one, and what's the rollback path from each failure point?

The lifecycle splits into three phase groups based on side-effect scope: A (read-only) can be aborted with no rollback work; B (local-only) writes target HCL to disk but doesn't touch the cloud, so rollback is just cp -r .backup/; C (production) changes real cloud resources and rollback requires the Recovery agent or terraform destroy.

The .backup/ wrapper from stakpak_arch.md section 28 is the linchpin of cheap rollback in group B: every file modification is preceded by moving the prior version to .backup/{run_id}/. If the user discards the plan after Generate, restoration is one cp. If the migration fails in group C, the audit log records exactly what happened and the Recovery agent has bounded options (destroy, state surgery, escalate). At every transition between phases, an AuditEntry is written via the after_tool_execution hook, chain-verifiable for compliance review.

LLD-3

Knowledge service — schema cache and RAG paths

When the Mapper needs to know "is aws_s3_bucket.acl valid in provider v5.30?" or "what's the GCP equivalent of an AWS ALB?" — how does libs/knowledge answer?

never expire (deterministic, reproducible) • "latest" lookups: 24h TTL (only used in dev/exploration, never production) • Stage 1 cache hit target: ≥95% on the Stage 1 GCP→AWS demo migration Article XII rule 2 — cache-first Order of operations on every Mapper call: exact lookup → vector search → cold LLM Cold LLM call is the last resort — costs tokens. ⚠ Stage 1 scope clarification Stage 1 ships the exact path only — schema cache + Terraform Registry fetch. The RAG path (LanceDB + corpus + embeddings) arrives in Stage 3. The interface (search_mappings) exists in Stage 1 as a stub returning Vec::new() so Mapper code compiles against the final API and the Stage 3 swap is a single function rewrite, not a refactor.

Two paths through libs/knowledge: exact lookup (deterministic schema fetch by (provider, version) tuple, hits SQLite first, falls back to registry.terraform.io on miss) and RAG lookup (semantic search through embedded mapping examples, returns top-K matches for fuzzy queries like "GCP equivalent of AWS ALB"). The Validator only uses the exact path; the Mapper uses both; the Cost Optimizer uses RAG to find cheaper alternatives.

Cache-first ordering (exact → vector → cold LLM) is operationalized as Article XII rule 2. The cache hit target is 95% on the Stage 1 demo migration; once corpus grows in Stage 3+, hit rates approach 99% and most migrations complete with zero cold LLM calls for mapping. Schemas pinned by version never expire — that's how Article VI (knowledge layer integrity) gets enforced. Cold "latest" fetches in production paths are a code smell.

LLD-4

Credential broker — how secrets never reach the LLM

When a tool needs {{secret:aws-prod}}, how does Terrashift resolve it without the LLM ever seeing the actual credential?

Rule 5 Don't bypass the proxy redaction layer. Step 6 is non-optional — even disabling redaction is not for production. Rule 7 Don't write disk-bound secrets to bypass UID issues. Container UID handoff (gosu) exists for this — use it. Rule 10 Don't store API keys in profiles outside ~/.terrashift/. Credential resolution chain depends on file location.

The contract: the LLM never sees a real credential value. It works with named references like {{secret:aws-prod}} that get resolved at the tool-execution boundary by the broker. Resolution always uses short-lived federated tokens (STS AssumeRole, GCP ADC + workload identity federation, Azure managed identity) — long-lived keys are never held in process memory.

Two redaction passes protect against secret leakage: (a) the broker substitutes {{secret:...}} references with real values only after the LLM has finished reasoning, and (b) the pre-prompt scrubber runs over every tool result before the next LLM turn, replacing detected secrets with [REDACTED:type:hash] tokens. After the tool returns, credentials are zeroized in memory using the zeroize crate. Every step writes an AuditEntry.

The same broker handles LLM provider API keys. When the customer's ~/.terrashift/config.toml references api_key_env = "ANTHROPIC_API_KEY", the broker resolves it at LLM-call time, hands the value to stakai for one request, then zeroizes. Provider keys never live as instance fields on the Client struct — same Article V protections apply. See LLD-6 for how model and provider get resolved through the 5-layer chain before this broker is even invoked.

LLD-5

MCP architecture — three servers, one redaction boundary

Where do the three MCP servers live, what tools do they expose, and where does the redaction layer sit?

Three MCP servers, three different sources of truth. terrashift-knowledge exposes our own schema cache and mapping corpus as MCP tools — Opus can answer "is this attribute valid?" without us hand-building the prompt. stakpak-reference runs the actual Stakpak binary in MCP mode, letting Opus call Stakpak's tools and observe its behaviour as a reference. filesystem-readonly-refs exposes ~/refs/ for the architecture document and source codebases.

All three sit behind the libs/mcp/proxy redaction boundary — every tool result passes through the same redaction layer before reaching the LLM, regardless of which upstream produced it. This is the operational point of Article V: there's exactly one place secrets get scrubbed, and bypassing it is Article XIII rule 5. mTLS is on by default; the in-memory CA at process startup means keys never touch disk.

LLD-6

Model resolution and provider configuration — 5-layer chain

When the customer types terrashift migrate --model openai/gpt-5 after editing ~/.terrashift/config.toml, which model actually gets used? Where do the layers merge?

Policy: tier→model mapping, max_turns, allowed_providers list, Validator on path Locked entirely (no override anywhere): • Article V redaction layer • Article XIII rule 5 (no proxy bypass) • audit log on, signing keys per migration Resolver silently drops policy-conflicting overrides. Late-binding — model can change between turns. Vec<ChatMessage> is provider-neutral; vendor-specific shape conversion happens fresh per request inside stakai/convert.rs. Switching model mid-conversation preserves history verbatim.

The 5-layer chain mirrors Stakpak exactly (per stakpak_arch.md section 11 + section 15). Operators set defaults at the bottom, customers override upward. Per-call overrides (Layer 5) are programmatic only and arrive in Stage 6+ when SaaS routes exist; Stage 1 ships layers 1-4. The merge logic lives in one place (libs/ai/src/resolver.rs) so every code path that resolves a model goes through the same priority rules — no drift, no surprise.

The policy/preference split is what makes Article V enforceable in a BYOK world. Customers control their own cost and quality trade-offs (preference fields take caller value). Operators lock the safety surface (policy fields silently override caller). And some fields are immutable across the entire system (the redaction layer, audit signing) — Article XIII rule 5 is operationalised by making these unreachable through any override path. The audit log records provider, model_id, and provider_endpoint on every LLM-touching entry so compliance reviewers can answer "which model produced this?" deterministically.
